Until the first mature release, Bonsai's own allowance overrun is non-blocking
for development. Continue reporting the actual root verdict and retained cost;
do not change inventory, coefficients, obligations, or deadlines to turn it into
a pass. Prioritize correctness and usable verification before self-host pruning.

## 1. Harden the first adapter

Bonsai's own `.feature` contracts execute through the real CLI against the
complete committed inventory. The native backend uses tsrs for TypeScript
semantics without a reference compiler pass; development tests compare it with
TypeScript separately. Its unused Oxc predecessor was deleted. Full self-budget
acceptance still requires retained-code reduction and remaining development/test
associations; complete feature evidence is separate from a budget pass. Fixed
Bun/Node entry points connect the CLI and its workers, preserving unused exports
and test/production boundaries. Test-helper chains inherit existing production
subjects without letting shared support justify unrelated code.

Profiles expose command, source, and verification durations, including interrupted
work. Native benchmarks use fresh processes and retain evidence completion state.
Expand real-project and diagnostic conformance for the sole native runtime;
known TypeScript 5/7 gaps remain explicit blockers. Keep the development oracle
outside the published package and validate releases from an isolated npm tarball. See [native scope](native-prototype.md)
and [performance evidence](performance.md).

- Profile nested verification and native graph transfer before further optimization; remove unused or duplicate semantic queries while preserving fresh programs and every observation.
- Add fixtures for re-exports, overloads, classes, type-only dependencies, binding helpers, and unsupported executable registration patterns.
- Extend the fixed subprocess adapter only from real launch patterns; computed targets and resource dependencies still need precise tracing and diagnostics. Runtime import/re-export initialization now has separate static relationships and type-only traversal state.
- Extend human explanations from the static contract paths and verification subjects now available in JSON.
- Keep versioned snapshot and evidence-v2 validation aligned with collector output. Checker/toolchain/Bun content identities, root lockfiles, effective configuration, and execution profiles now bind the local facts; authentic execution remains a separate deployment requirement.
- Calibrate inventory and size pressure on real repositories before treating the coefficients as defaults.

Done when representative TypeScript projects can be analyzed without silently dropping maintained dependencies.

## 3. Trusted merge admission

Current CI validates the pull-request merge result and separates candidate
commands from write-capable jobs. It still runs the checker and scripts supplied
by that checkout. Local worker separation and content fingerprints do not make
this a trusted admission deployment.

Deliver one concrete GitHub deployment in dependency order:

1. **Pin inputs outside the candidate.** Obtain an immutable checker artifact and
   its dependencies independently of candidate source. Resolve policy, maintained
   inventory, and required verification profile from a protected revision. Bind
   the request to the exact merge commit/tree, policy revision, and checker
   identity. Candidate CLI/environment overrides cannot select these inputs.
2. **Establish the execution boundary.** Run candidate handlers and supporting
   runners without publisher credentials or write access to the trusted checker,
   policy, or evaluator. Use an external sandbox with bounded resources and
   cleanup; ordinary child processes are insufficient. Validate versioned,
   identity-bound evidence at the trusted boundary. Identity validation alone
   does not prove authentic execution: the deployed runner must prevent candidate
   code from fabricating the authoritative result.
3. **Publish and require the decision.** A separate trusted publisher records a
   result only for that request's exact combined tree. Wire pull requests and
   `merge_group` candidates to the same gate, then configure repository rules to
   require the trusted check. Missing, stale, cancelled, or incomplete execution
   must block admission. Policy/inventory changes require separate governance
   review rather than acceptance under candidate-relaxed rules.

Before enabling enforcement, demonstrate these stakeholder examples against a
disposable repository: a candidate that enlarges its local allowance still uses
the protected policy; forged or replayed worker output cannot obtain success; a
changed merge tree needs fresh evidence; and two changes that each fit alone are
rejected when their combined retained cost exceeds the ceiling. Keep the
combined-cost example in a calibrated consuming fixture while Bonsai's own
pre-maturity overrun remains non-blocking development information.

The versioned evidence boundary precedes external runner integration; runner
coverage/mutation requirements become mandatory only when their concrete
adapters and reviewed policy floors exist. Trusted deployment also needs an
immutable checker distribution, sandbox infrastructure, and repository-rule
configuration; adding a candidate-controlled workflow cannot supply those trust
anchors.

Done when a candidate cannot alter its own acceptance rules or bypass combined-tree evaluation.
