# Next milestones

## 1. Harden the first adapter

Bonsai's own `.feature` contracts execute through the real CLI against the
complete committed inventory. The native backend uses tsrs for TypeScript
semantics without a reference compiler pass; development tests compare it with
TypeScript separately. Its unused Oxc predecessor was deleted. Full self-budget
acceptance still requires executable entry-point relationships and retained-code
reduction; complete feature evidence is separate from a budget pass.

Profiles expose command, source, and verification durations, including interrupted
work. Native benchmarks use fresh processes and retain evidence completion state.
Expand real-project and diagnostic conformance before adopting a native default;
known TypeScript 5/7 gaps remain explicit blockers. See [native scope](native-prototype.md)
and [performance evidence](performance.md).

- Add fixtures for re-exports, overloads, classes, type-only dependencies, binding helpers, and unsupported executable registration patterns.
- Track side-effect imports and resource dependencies, with precise unresolved-edge diagnostics.
- Extend explanation output to show actual contract-to-component paths and verification subjects.
- Version and validate serialized snapshot/evidence schemas; bind evidence to checker, toolchain, lockfile, and execution profile identities.
- Calibrate inventory and size pressure on real repositories before treating the coefficients as defaults.

Done when representative TypeScript projects can be analyzed without silently dropping maintained dependencies.

## 2. Real runner and effectiveness evidence

- Reuse Cucumber execution messages and Vitest results where teams already run them.
- Keep structural references, runtime coverage, mutation detection, and passed contract observations separate.
- Attach Stryker mutation evidence and enforce explicit quality floors without granting extra size allowance.
- Attribute lower-level tests and their exclusive fixtures while preserving all contractual obligations during test deletion.

Done when missing, interrupted, skipped, stale, or ineffective verification blocks the configured gate reliably.

## 3. Trusted merge admission

- Distribute a pinned checker independently of candidate source.
- Read effective policy from a trusted revision, including the maintained inventory and evidence profile.
- Run contract and supporting verification in an isolated candidate environment.
- Evaluate the actual merged tree through pull-request and merge-queue workflows.
- Require branch protection checks; test two individually acceptable changes that exceed the ceiling together.
- Treat policy changes as separately reviewed governance changes.

Done when a candidate cannot alter its own acceptance rules or bypass combined-tree evaluation.

## 4. Expand only from concrete demand

Choose the next framework adapter from a real consuming project: HTTP route registration, queue handlers, dependency injection, or another language. Preserve one generated registry and one evaluator. Avoid feature budget ledgers, confidence scores, and semantic uniqueness scoring.
