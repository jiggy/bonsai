# Purpose

Arrange isolated projects and observe Bonsai's actual public CLI for its executable specifications.

## Ownership

`cli.ts` owns real synchronous and asynchronous CLI launches. `project.ts` owns disposable fixture files and policies. Domain helpers arrange inputs and return CLI reports or independently observed filesystem/process facts. `actions.ts` binds the stable public command identities. `control-depth.ts` arranges equivalent nested and guard-clause applications under an explicit structural policy. Its real nested check explicitly uses the supported serial mode: both application observations still execute, while worker isolation remains covered by its dedicated contracts and regressions.

## Local Contracts

- Use the real CLI and production native checker. Helpers must not calculate expected policy decisions or mark observations passed.
- Keep fixtures independent and remove them in `finally`. Runtime logs and markers stay outside their explicit maintained input lists.
- Keep action names aligned with public operations. Fixture names, extra cases, and helper result aliases must not manufacture product allowance.
- Preserve product promises and regression coverage across layers. Move technical assertions into explicit tests rather than preserving them as allowance-earning selectors. Name the destinations in review.
- Keep network installation checks in release validation, outside ordinary feature verification.
- Do not raise the root deadline, change its coefficients, or exclude authored files to accommodate these specifications.

## Work Guidance

`ux.ts` returns each check's own canonical report; output mode and copied retries do not create new namespaces for the same facts. Exact wrapping and timing headings remain technical observations. Product checks inherit the normal CLI environment; terminal and locale overrides are supplied by technical tests. Copied retries receive their bootstrap paths as quoted shell arguments. `basic.ts` observes application loading separately from handler calls and projects actual requirement content in canonical order without removing duplicates. `verification.ts` identifies waiting work from observed start events at a live interruption barrier; input IDs do not identify queue position. `accounting.ts` checks the base and pruned revisions separately under the same reviewed policy.

Use named imports, fixed module-relative CLI entry points, and explicit subprocess option properties so the current adapter can trace the specification-to-implementation connection.

Keep technical-only fixtures and assertions in `test/`; acceptance support must not import test modules. Shared arrangements may be reused by technical tests. Prefer a raw public report over cosmetic projections, and use independent logs, byte comparisons, or process observations when the product consequence needs them. Never return an opaque scenario verdict or compute the expected policy answer.

State the arranged context in feature prose, not only a fixture identifier. Keep each canonical action limited to its named public operation; another command's result must not be nested under it to create more surface.

The trusted-budget example accesses its Git checkout through a symlink, exercising real root-identity validation on every host. Keep the alias outside the target tree, clean up both paths, and let the CLI resolve identity rather than canonicalizing away the example's context.

`runners.ts` arranges a real Bun assertion and a Vitest-compatible report to distinguish configured supporting success, failure, skipped work, and stale output. It is not an installed Vitest runner; pinned framework compatibility belongs in the explicit technical smoke test. Do not manufacture passed product observations or gate decisions in this arrangement.

## Verification

`bun run test:specs -- --scenario NAME` provides focused authored-example feedback. `bun run test:features` executes all product contracts through the full root gate and archived checker. `bun run test:spec-sensitivity` proves selected authored observations reject controlled product faults in disposable copies. See [the BDD guide](../../docs/bdd.md).
